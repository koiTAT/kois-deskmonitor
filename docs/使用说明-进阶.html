DeskMonitor 使用说明（进阶版）

> 面向：知道 CPU / 内存的基本概念，想知道**每个数字具体怎么算出来**的人。

>

> 只想看懂界面的话，看 [使用说明.md](使用说明.md)。

---

0. 数据来源总述

全部来自 macOS 公开接口，**没有私有 API、不需要 root、不安装内核扩展、不联网**：

框架用途
`mach`（`host_processor_info` / `host_statistics64`）CPU、内存
`sysctl`（`vm.swapusage` / `NET_RT_IFLIST2` / `hw.perflevel*`）交换、网络、硬件信息
`IOKit`（`IOBlockStorageDriver` / `IOAccelerator`）磁盘 I/O、GPU
`libproc`（`proc_listallpids` / `proc_pidpath` / `proc_pidinfo`）进程
`AppKit`（`NSWorkspace`）应用清单与图标

采样在独立的串行队列（`qos: .utility`）上执行，结果回到主线程刷新界面。

2. CPU

2.1 总量


host_processor_info(mach_host_self(),
                    PROCESSOR_CPU_LOAD_INFO,
                    &count, &info, &infoCount);

每个逻辑核返回一个 `processor_cpu_load_info`，内含 4 个 `UInt32` tick 计数器：


cpu_ticks[0] = USER   cpu_ticks[1] = SYSTEM
cpu_ticks[2] = IDLE   cpu_ticks[3] = NICE

这些是**从开机起的累计 tick 数**，所以要保存上一次的值做差分：


busy  = Δuser + Δsystem + Δnice
total = busy + Δidle
usage = busy / total

两个细节：

  • **计数器是 `UInt32`，会回绕**，所以差值必须用 `&-`（wrapping 减法），不能用普通减法。
  • 首次采样没有基准，直接返回 0 并记下基准值，第二次才是真实数据。

2.2 每核

同一份数组按核切片，逐核套用上面的公式即可。柱状图高度 = `usage × 30pt`。

2.3 核心编号与 P/E 顺序

柱状图下方的编号 `1..N` 就是内核返回的数组下标 `0..N-1`。

**关键：Apple Silicon 上能效核排在前面，性能核排在后面。**

这不是猜的，是实测出来的。验证方法：


# 起 4 个单线程满载进程
for i in 1 2 3 4; do (while :; do :; done) & done
# 观察哪些核被打满
./DeskMonitor --probe

结果：只有**最后 4 个**核到了 99–100%，前 6 个维持在 20–50%。

因此：


编号 1–6   → 能效核 E（Efficiency）
编号 7–10  → 性能核 P（Performance）

性能核数量来自 `sysctl hw.perflevel0.logicalcpu`（本机 = 4），能效核是 `hw.perflevel1.logicalcpu`（= 6）。

代码里做了防御：如果两个 perflevel 之和不等于总核数（例如 Intel 机器上 perflevel 不存在），就退化成单色柱状图，不做任何 P/E 假设。

2.4 `4P + 6E` 是什么意思

记号含义本机数量
PPerformance，性能核。频率高、单核强、耗电4
EEfficiency，能效核。频率低、省电、适合后台6

调度由 macOS 内核决定，**App 无法指定**某个线程跑在哪类核上。系统会让前台重活优先落到 P 核，后台任务放到 E 核。

这就是为什么平时大部分柱子很矮：E 核在干轻活，P 核大部分时间睡着。

3. 内存

3.1 数据源


host_statistics64(mach_host_self(), HOST_VM_INFO64, ...);

拿到 `vm_statistics64`，页大小在 Apple Silicon 上是 **16 KB**（`vm_kernel_page_size`）。

3.2 四个量的计算

显示公式对应字段
应用`(internal_page_count − purgeable_count) × pageSize`匿名、非可清除
联动`wire_count × pageSize`内核锁定
压缩`compressor_page_count × pageSize`压缩器占用
缓存`(external_page_count + purgeable_count) × pageSize`文件页

其中**缓存**是"随时可丢弃"的，所以不计入「已用」。

3.3 与「活动监视器」的对应关系

活动监视器本面板
应用内存应用
联动内存联动
已压缩压缩
已缓存文件缓存
已使用内存应用 + 联动 + 压缩

3.4 压缩的两个数字

`vm_stat` 里有两个容易混淆的字段：


Pages stored in compressor:      689716   ← 压缩前的原始数据量
Pages occupied by compressor:    286102   ← 压缩后实际占用

面板显示的是**后者**（真实占用）。前者除以后者就是压缩率，本机实测约 **2.4 倍**：


689716 × 16KB ≈ 10.5 GB 原始数据
286102 × 16KB ≈  4.4 GB 实际占用

所以「压缩 4.9 GB」不代表只用了 4.9 GB，它装着的原始数据接近 11 GB。

3.5 为什么「已用」不会超过物理内存

应用 + 联动 + 压缩三者都实打实占着物理页，所以它们的和天然 ≤ 总内存。超出物理内存的需求不会体现在这个数字上，而是变成**交换**。

4. 交换


sysctl vm.swapusage   →   struct xsw_usage
字段含义
`xsu_total`系统当前**已创建**的交换文件总容量
`xsu_used`已写入的量

**`xsu_total` 不是上限，也不是建议值。** macOS 的 `dynamic_pager` 按需创建交换文件（`swapfile0`、`swapfile1`……），不够就再建一个。真正的边界是磁盘剩余空间。

因此面板只显示 `xsu_used`，总量放进悬停提示——写成「已用 / 总量」会让人误读成"快满了"。

5. 网络


sysctl(CTL_NET, PF_ROUTE, 0, 0, NET_RT_IFLIST2, 0)

返回一串 `if_msghdr2`，其中 `ifm_data` 是 `if_data64`，含 64 位累计字节数。

**只统计 `en*`（以太网 / Wi-Fi）和 `pdp_ip*`（蜂窝）**，避免 VPN 隧道（`utun*`）与物理网卡重复计数。

坑：实际只有低 32 位

实测本机 en1：

来源Ibytes
`netstat -ibn`21,929,251,512
`NET_RT_IFLIST2`384,832,512

后者恰好等于前者 `mod 2³²`。用 C 重写同样逻辑，结果一致——确认是内核侧行为，不是 Swift 结构体绑定问题。

后果：计数器每 4 GB 翻转一次。若直接做 64 位减法，高速下载时会周期性产生天文数字的速率尖峰。所以差值必须按 32 位回绕处理：


let delta = (current &- previous) & 0xFFFF_FFFF

对真实 64 位计数器同样安全——1 秒内不可能流过 4 GB。

验证：`curl` 自报 4.47 MB/s，`netstat` 同窗口 4.69 MB/s，采样值 3.6–5.5 MB/s。

7. GPU


IOServiceMatching("IOAccelerator")
→ "PerformanceStatistics"["Device Utilization %"]

多个加速器时取最大值，归一化到 0–1。

特点：**Apple Silicon 上无需 root**。局限：不提供显存占用、频率、温度；Intel 机器上部分字段可能缺失，缺失时显示「不可用」。

8. 进程

8.1 枚举与归并

  • `NSWorkspace.shared.runningApplications` → 取 `activationPolicy == .regular` 的 App（有 Dock 图标的）
  • `proc_listallpids` → 拿到所有 pid
  • 每个 pid 调 `proc_pidpath` 取可执行文件路径
  • 路径以某个 App 的 `bundleURL.path + "/"` 开头 → 归入该 App

**为什么必须归并**：Chrome、Edge、Steam、VSCode 这类应用的负载几乎全在 Helper 子进程里，主进程常年 0%。只统计主进程会得出完全错误的结论。

Steam 的实际分布（本机实测 10 个进程）：

进程数量
`steam_osx`1
`ipcserver`1
`Steam Helper`8

8.2 CPU 百分比


proc_pidinfo(pid, PROC_PIDTASKINFO, 0, &info, sizeof(info))

拿到 `pti_total_user` / `pti_total_system`。

**单位是 mach 绝对时钟 tick，不是纳秒。** Apple Silicon 上是 24 MHz，必须换算：


var tb = mach_timebase_info_data_t()
mach_timebase_info(&tb)
let seconds = Double(ticks) * Double(tb.numer) / Double(tb.denom) / 1e9

> 直接当纳秒用会低估约 **41.7 倍**。实测：单线程满载 2 秒 = 46,568,981 tick，

> 46,568,981 ÷ 24e6 = 1.94 秒，与墙钟吻合。

然后：


usage = Σ(Δuser + Δsystem) / 墙钟间隔

**单位是「核」**：`1.0 = 100% = 吃满一个核心`。多线程应用会超过 100%，10 核机器理论上限 1000%。

8.3 内存

`pti_resident_size`（RSS）按 App 求和。

**偏差**：多个进程共享同一批系统库，RSS 求和会把这些共享页重复计算多次，所以比「活动监视器」的物理占用偏高。这是 RSS 口径的固有特性，不是 bug。

8.4 沙盒限制

App Sandbox 下 `proc_pidpath` / `proc_pidinfo` 对非自身进程返回 `EPERM`，进程列表整体失效。当前版本是无沙盒构建；上架版本需要把这个模块关掉。

9. 阈值与配色

对象规则
内存「交换」< 256 MB 灰；≥ 256 MB 黄；≥ 1 GB 红
内存压力徽标正常 / 偏高 / 严重（`kern.memorystatus_vm_pressure_level` = 1 / 2 / 4）
进程 CPU占整机 < 30% 白；30–60% 黄；> 60% 红
顶部状态圆点取内存告警与压力的最高等级

进程 CPU 的颜色按**占整机比例**判断，不是按「吃了几个核」。100% 在 10 核机器上只占整机 10%，标红会误导用户。

---

10. 已知偏差与限制

  • **进程内存偏高**：RSS 求和重复计算共享库（见 8.3）。
  • **只统计有 Dock 图标的 App**：纯后台的辅助进程不单独列出。
  • **网络不含 VPN 隧道**：只算物理网卡，`utun*` 不计。
  • **无温度 / 风扇 / 功耗**：需要 root 或 SMC 访问，当前不做。
  • **GPU 字段依赖 IOKit 私有属性名**：`Device Utilization %` 未公开承诺，未来系统版本可能变化，找不到时显示「不可用」。
  • **APFS 容量**：`statfs` 返回的是容器层面的数字，与其他卷共享空间，可能与本卷实际可用略有差异。
  • **核心 P/E 顺序**：基于本机实测（M4）。跨代芯片未逐一验证，代码在数量不匹配时会退化为单色显示。
